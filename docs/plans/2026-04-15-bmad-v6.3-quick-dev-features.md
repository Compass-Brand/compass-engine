# BMAD v6.3.0 — Quick-Dev Feature Parity Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Bring our quick-dev workflow to v6.3.0 feature parity: epic context compilation, previous story continuity, planning artifact awareness, and one-shot spec trace.

**Architecture:** **Port features into our custom override** (strategy b). Lift-and-shift is infeasible: our custom `workflow.md` and `steps/step-01-mode-detection.md` replace the upstream flow entirely, with Compass-specific Mode A/B routing, escalation tiers that delegate to `bmad-compass-quick-spec`, and a 6-step linear pipeline (mode-detection → context-gathering → execute → self-check → adversarial-review → resolve-findings) that has no analogue to upstream's `clarify-and-route → plan → implement → review → present`. Re-adopting upstream wholesale would delete our adversarial-review loop and compass-quick-spec escalation — both deliberately engineered. Instead, we port the three v6.3.0 capabilities into our custom flow's existing hook points, refresh the stale `native/` mirror for reference fidelity, and treat the `spec-wip.md → spec-{slug}.md` change as a cross-cutting cleanup in both `native/bmad-quick-dev` (dead files — fix for hygiene) and `custom/compass-skills/bmad-compass-quick-spec` (live — fix for correctness).

**Tech Stack:** BMAD skill workflows, markdown step files, sub-agents, YAML frontmatter (spec status lifecycle).

**Beads:** bmad-engine-zeml, bmad-engine-tkpg, bmad-engine-a0iq

**Upstream references:** PR #2185 (planning artifact awareness), #2201 (previous story continuity), #2218 (epic context compilation), #2214 (spec-wip → spec-slug), #2121 (one-shot spec trace).

## ⚠️ Critical preconditions — read before executing

1. **Spec status lifecycle:** Feature 2 (continuity) depends on specs reaching `status: done`. Today **nothing in our codebase writes `done`** — `bmad-compass-quick-spec/step-03-generate.md` writes `review`, `step-04-review.md` writes `ready-for-dev`, and our `bmad-quick-dev` never writes spec frontmatter at all. **Cross-cutting Task 7 below adds the `done` write-back.** Without it, Feature 2 silently finds zero candidates.
2. **Test strategy:** workflow steps are LLM-interpreted markdown, not deterministic code. JS-helper unit tests prove the helper works but NOT that the workflow uses it correctly. Strategy adopted in this plan: (a) extract helpers to `tools/quick-dev-scan.js` invoked by the markdown step via explicit shell-out, (b) add markdown-lint structural tests asserting required headings/state-vars/NEXT directives are present, (c) add at least one dogfood smoke run per feature in Phase-2 verification. All three layers required — JS unit tests alone are insufficient.
3. **State variable precedence:** when both `{epic_context_path}` (Feature 1) and `{planning_context_files}` (Feature 3) are set, Feature 1 wins. Step-02 must explicitly check `{epic_context_path}` first and ignore `{planning_context_files}` when it is set.
4. **Single-PR groupings:** Feature 1 task 3, Feature 2 task 3, and Feature 3 task 2 all extend the same section of `step-01-mode-detection.md`. They MUST land as a single PR to avoid merge conflicts and partial-state semantics. Marked "PR-A" below.
