## What bmad-init currently does

Per `src/bmad/modules/native/core-skills/bmad-init/SKILL.md`:

1. **Fast path (`bmad_init.py load`):** reads existing `_bmad/{module}/config.yaml` and returns JSON vars.
2. **Init path (`check` / `resolve-defaults` / `write`):** walks user through first-time setup, writes `_bmad/core/config.yaml` and `_bmad/{module}/config.yaml`.

It's **not pure config loading** — it also handles first-time bootstrap. In v6.3.0 upstream, this bootstrap responsibility is shifted to install-time (the installer writes configs) or to each skill handling "file missing" on its own.

**Risk:** After removing bmad-init, nothing in our shipped bundle bootstraps a missing config. Call this out under "Risk callouts" below.

## Build/manifest touchpoints (tools/build.js audit)

Confirmed `tools/build.js` has **no special casing for bmad-init**. The skill is picked up generically by:
- `buildBmadSkills()` → `mergeModules()` copies whatever is under `src/bmad/modules/native/core-skills/`.
- `generateSkillManifest()` (lines 351–395) derives entries by scanning for `**/SKILL.md`.
- `generateBmadHelp()` (lines 318–349) concatenates each module's `module-help.csv`.
- `generateAgentManifest()` ignores bmad-init (not type=agent).
- `generateClientSkills()` emits a client skill for every row in `skill-manifest.csv`.

**Implication:** Deleting the `bmad-init/` directory + removing the CSV row auto-removes bmad-init from all generated manifests and client bundles on the next build. No build-script edits required.

**Validation touchpoints in `tools/validate.js`:** none reference bmad-init by name. `validateSkillFormat` scans all SKILL.md; it will not fail after deletion. `validateModuleHelpDeps` checks before/after refs — no row currently references bmad-init as a dep.
