# BMAD v6.3.0 — Installer Bootstrap Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Provide a bootstrap path that writes `_bmad/{core,bmm,...}/config.yaml` on first install so the bmad-init removal in `bmad-engine-lg73` Task 11 doesn't break fresh installs.

**Architecture:** **Option (a) — `compass-engine init` command writes configs from defaults.** A new `init` subcommand reads the question schema from each module's `module.yaml` (already there: prompt + default + result template), resolves all defaults, and writes `_bmad/{core,$module}/config.yaml`. Default mode is non-interactive (uses defaults silently). `--interactive` flag drives a TTY prompt loop for users who want custom values. Push.js gains an opt-in `--init` flag to trigger this after a first-time delivery to a downstream project. Rejected option (b) — per-skill "if missing, prompt" fallback — because it scatters bootstrap responsibility across 24+ skills and depends on per-LLM prompt behavior; option (a) makes bootstrap a deterministic install-time act.

**Tech Stack:** Node.js, YAML (js-yaml or native), src/cli.js, tools/push.js, JSON for inter-step state

**Beads:** bmad-engine-the2 (BLOCKS bmad-engine-lg73 Task 11)

**Upstream context:** BMAD v6.3.0 removed `bmad-init` entirely (PR #2159). Upstream relies on its own installer (`BMAD-METHOD/tools/installer/`) to write configs at install time. Compass distributes via `tools/push.js` — never invokes the BMAD installer — so Compass needs its own bootstrap path.

## Investigation summary

- `src/cli.js`: 85 lines. Pure dispatcher routing to `tools/build.js`, `push.js`, `validate.js`, `create-bmad-module.js`, drift-check scripts. No interactive setup, no YAML write.
- `src/bmad/modules/native/core-skills/bmad-init/scripts/bmad_init.py`: source of truth for current bootstrap behavior. Subcommands: `load`, `check`, `resolve-defaults`, `write`. We are NOT porting this Python script into Node; we are reading its question schemas from `module.yaml` files (which `bmad_init.py` already does) and re-implementing the write step in Node.
- Question schemas live in `module.yaml` files:
  - Core: `src/bmad/modules/native/core-skills/bmad-init/resources/core-module.yaml` — vars `user_name`, `communication_language`, `document_output_language`, `output_folder`.
  - BMM: `src/bmad/modules/native/bmm-skills/module.yaml` — vars `project_name`, `user_skill_level`, `planning_artifacts`, `implementation_artifacts`, `project_knowledge`. Also a `directories:` list to create.
  - Compass + bmad-builder modules: their `module.yaml` files declare no user-facing vars (per config-migration plan, their agents load from `_bmad/core/config.yaml` instead).
- Result template syntax: `result: "{project-root}/{value}"` etc. Need to support `{value}`, `{project-root}`, and references to other resolved vars (e.g., bmm's `planning_artifacts` defaults to `{output_folder}/planning-artifacts`).
- After `bmad-engine-the2` ships, capture defaults from `bmad_init.py` + `core-module.yaml` into a runbook BEFORE `bmad-engine-lg73` Task 11 deletes the bmad-init directory.

## Risk callouts

- **Idempotency:** `compass-engine init` must refuse to overwrite by default. Existing user customizations to `_bmad/{core,bmm}/config.yaml` MUST survive a re-run. Test this explicitly (Task 6).
- **YAML quoting:** values containing colons or special chars must be quoted on write. `js-yaml.dump` handles this — verify in Task 6 with a test fixture containing `user_name: "Mary: PM"`.
- **Backwards-compat for already-installed Compass projects:** existing repos have NO `_bmad/{core,bmm}/config.yaml` — they relied on bmad-init's lazy bootstrap. Document the migration path in Task 10's runbook: `compass-engine init` is safe and additive (refuses overwrite) so existing repos can run it post-upgrade.
- **`compass`/`bmad-builder` modules:** these have NO user-facing vars in their `module.yaml` files. Per the config-migration plan, their agents load from `_bmad/core/config.yaml`. Skip writing `_bmad/compass/config.yaml` and `_bmad/bmad-builder/config.yaml` — they would be empty files. If a future module gains user-facing vars, add it to the `--modules` default list.
