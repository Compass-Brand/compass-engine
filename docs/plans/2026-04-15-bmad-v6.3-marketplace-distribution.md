# BMAD v6.3.0 — Marketplace Distribution Audit & Adoption Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Audit our distribution model against BMAD v6.3.0's marketplace pattern, then adopt PluginResolver where it adds value without breaking our flow.

**Architecture:** Three-phase approach. Phase 1 (lkja) is read-only: we catalogue our `tools/build.js` + `tools/push.js` pipeline, the upstream PluginResolver + marketplace.json + registry-client stack, and produce a written diff between the two. Phase 2 is a single decision document (ADR) that picks an adoption posture based on Phase 1 findings. Phase 3 (uscr) is conditional TDD work gated on the ADR outcome — it may be anything from "no code changes" to a full PluginResolver integration shim.

**Tech Stack:** Node.js (ESM for compass-engine, CJS for BMAD-METHOD installer), `BMAD-METHOD/tools/installer/`, `.claude-plugin/marketplace.json`, YAML module manifests, CSV help manifests, Git submodules.

**Beads:** bmad-engine-lkja, bmad-engine-uscr

## Context Summary (from investigation)

**Our pipeline (`tools/build.js`, 628 lines; `tools/push.js`, 693 lines):**
- `build.js` merges `src/bmad/modules/native/{bmm,core}-skills/` (upstream mirror) with `src/bmad/modules/custom/{bmm,core}-skills/` (Compass overrides, custom-wins) plus two custom-only modules `compass-skills/` and `bmad-builder-skills/` into `dist/_bmad/{bmm,core,compass,bmad-builder}/`. It then generates three manifests at `dist/_bmad/_config/`: `agent-manifest.csv`, `bmad-help.csv`, `skill-manifest.csv`, and fans out `SKILL.md` stubs to `dist/.claude/skills/`, `dist/.opencode/skills/`, `dist/.codex/skills/` via `clientSkillName()` remapping.
- `push.js` replicates `dist/*` into downstream Compass projects (`compass-forge`, `compass-services`, `compass-initiative`, etc.). Nine targets (`bmad`, `planning`, `documentation`, `claude`, `codex`, `opencode`, `github`, `root`, `beads`) with two sync modes: full replace (with `localOnly` backup/restore) and `managed` (manifest-tracked stale-file cleanup, manifests stored under `.git/compass-engine-*-sync.json` when a git directory exists, falling back to `<projectPath>/.compass-engine/compass-engine-*-sync.json` otherwise). Feature subsetting exists for `github` and `root` bundles.
- No network fetch. No PluginResolver. No `marketplace.json`. No upstream installer is ever invoked — our distribution bypasses `BMAD-METHOD/tools/installer/` entirely.

**Upstream v6.3.0 stack:**
- `BMAD-METHOD/.claude-plugin/marketplace.json` — schema: `{name, owner, description, license, homepage, repository, keywords, plugins[]}` where each plugin has `{name, source, description, version, author, skills[]}`. `source` is a relative repo path; `skills[]` is an array of relative skill-directory paths. Our root ships two plugins: `bmad-pro-skills` (core-skills subset) and `bmad-method-lifecycle` (bmm-skills). No module.yaml at marketplace level — `PluginResolver` infers it.
- `BMAD-METHOD/tools/installer/modules/plugin-resolver.js` — **5 strategies, tried in order**:
  1. **Root module files** — `module.yaml` + `module-help.csv` exist at the common parent directory of all listed skills.
  2. **Setup skill** — a skill whose directory ends in `-setup` contains `assets/module.yaml` + `assets/module-help.csv`.
  3. **Single standalone skill** — exactly one skill listed, with both files in its `assets/`.
  4. **Multiple standalone skills** — every listed skill has its own `assets/module.yaml` + `assets/module-help.csv` (each becomes its own module).
  5. **Synthesized fallback** — neither file found; synthesize `module.yaml` from plugin metadata and `module-help.csv` from SKILL.md frontmatter (13-column format).
- `BMAD-METHOD/tools/installer/modules/external-manager.js` — fetches `https://raw.githubusercontent.com/bmad-code-org/bmad-plugins-marketplace/main/registry/official.yaml` via `RegistryClient`, falls back to bundled `registry-fallback.yaml` (#2228).
- `BMAD-METHOD/tools/installer/modules/community-manager.js` — fetches `registry/community-index.yaml` + `categories.yaml` from the same marketplace repo, returns empty on network failure (#2229 three-tier browser).
- `BMAD-METHOD/tools/installer/modules/custom-module-manager.js` — `parseSource()` accepts HTTPS Git URLs (any host, with `/tree/branch/subdir` extraction), SSH URLs (`git@host:owner/repo`), and local paths (`/`, `./`, `../`, `~`). Clones, reads `.claude-plugin/marketplace.json`, delegates to PluginResolver (#2233 universal source).
- Changelog v6.3.0 explicitly: "Remove custom content installation feature; use marketplace-based plugin installation instead (#2227)" — the old `--custom-content` flag is gone, replaced by `--custom-source <sources>` on the `install` command.

**Conflict / overlap analysis (preliminary, to be validated in Phase 1):**
- Our `src/bmad/modules/custom/` tree is **not** the same concept as removed "custom content" — that feature was an upstream installer flag (`--custom-content`) for end-users to sideload their own modules at install time. Ours is a build-time overlay that merges into `native/` before anything ships. Naming collision, not semantic collision.
- However: downstream Compass projects receive our bundle via `push.js` — they never run the BMAD installer. If a downstream project *also* wants to add its own custom plugins via the new `--custom-source` flag, they currently have no path (we don't ship the installer, only the generated `_bmad/` tree).
- Our generated manifests (`skill-manifest.csv`, `agent-manifest.csv`, `bmad-help.csv`) duplicate what PluginResolver strategies 1/4 would produce if we shipped a `.claude-plugin/marketplace.json` instead.

- Create `planning/decisions/adr-0001-marketplace-adoption.md` (establishes the `planning/decisions/` directory — none exists today).
- Template:
  - Context (summarize Phase 1 findings in ≤15 lines, cite #2227, #2228, #2229, #2233)
  - Options considered (at minimum these four):
    1. **Status quo** — keep bespoke build/push, no adoption. Reason: works today, no downstream breakage.
    2. **Ship marketplace.json alongside existing build** — add `.claude-plugin/marketplace.json` to our repo root covering `bmm`, `core`, `compass`, `bmad-builder` as four plugins so *external* consumers (not our pushed projects) can install via upstream CLI. Keep build/push unchanged.

## Risks & Backwards-Compatibility Callouts

**CRITICAL — downstream install breakage:** Every Compass project that consumes `push.js` depends on the *exact* `dist/` structure we produce today. Any change to `dist/_bmad/` layout, manifest schemas, or `push.js` target list ripples into `compass-forge`, `compass-services`, `compass-initiative`, `compass-modules`, `compass-brand-infrastructure`, `compass-brand-setup`, `mcps`, plus two `compass-services/*` subprojects. Before any Phase 3 merge: run `node tools/push.js --dry-run --all` and diff the planned changes across all discovered projects.

**Schema drift risk (#2227):** Removing `--custom-content` upstream did not touch downstream bundle consumers — our bundles don't invoke the installer. But if we adopt Option 4, every downstream project must install an installer (new dependency) before it can consume our changes. That is a user-visible operations change.

**Manifest byte-stability:** `skill-manifest.csv` is referenced by `generateClientSkills()` to produce the fan-out. Any row-order or schema change breaks the 90+ generated client skills (`validateBuild()` asserts ≥90). If Option 3 is chosen, treat byte-stability as an acceptance criterion — add fixture regression tests before swapping generators.

**Submodule coupling (#2233 fix):** PR #2233 fixed a version-walk bug in marketplace.json resolution. If we adopt, we must pin `BMAD-METHOD` submodule to ≥v6.3.0 and add a CI check so downgrade attempts fail loudly.

**Network-dependency creep (#2228):** Upstream now hits GitHub raw URLs at install time. If we import PluginResolver only (Option 3), we avoid this entirely — PluginResolver is a pure function over a cloned repo. Do NOT import `external-manager.js` or `community-manager.js` without an explicit ADR decision; those introduce network I/O into our deterministic build.

**Third-party supply-chain risk:** `external-manager.js` and `community-manager.js` fetch plugin metadata from `bmad-code-org/bmad-plugins-marketplace` — a GitHub repository **not under Compass control**. If that repo is compromised, installer-driven downstream installs would execute attacker-controlled plugin metadata (which can resolve to attacker-controlled Git URLs via PluginResolver strategy 5 fallback). **ADR constraint:** Compass installs (Options 2-5) MUST NOT consult `community-manager` or `external-manager` at runtime. Pin to local marketplace.json + bundled fallback only.

**Enforcement (test, not advice):** add `test/no-network-managers.test.js` (Phase 3 prerequisite for any option that touches PluginResolver) that fails if any file under `tools/` or `src/` `require()`s or imports `external-manager.js` or `community-manager.js`. Implementation: walk both directories, parse import statements, assert zero matches. This converts the constraint from advisory text into a CI-enforced invariant.

**Stateful sync-manifest backwards compat:** Existing downstream Compass repos already have `.git/compass-engine-{target}-sync.json` files on disk tracking what the previous push delivered. If Phase 3 renames any target (e.g., adds `claude-plugin`) or changes manifest schema, stale on-disk manifests must be migrated, not silently overwritten. **Action for Option 2 Task 3.2.5:** add a one-time manifest-migration step in push.js that detects pre-v6.3 schema and rewrites it.

**Sequence assertion:** Phase 2 must close before any Phase 3 task starts. If unclear mid-implementation, stop and amend the ADR rather than make implicit choices.
